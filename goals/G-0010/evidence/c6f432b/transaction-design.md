## Lock scope and dependency ordering

`Booking.Service.reserve` in `core/src/main/java/dev/parkcommerce/core/Booking.java` obtains and checks the pricing quote before it calls `store.transact(eventId, ...)`. Production `BookingApi.Wiring` supplies the HTTP `Pricing.Client` via `RemoteCalls.get`. Confirmation and recovery use persisted hold/order state; they do not fetch pricing. `JdbcBookingStore.transact` configures Spring's transaction template as `READ COMMITTED` with a ten-second transaction timeout, then executes `SELECT * FROM events WHERE id=? FOR UPDATE` before loading or changing that event's ledger. The JDBC pool is limited to ten connections in the application configuration; the contention test overrides it to 32 scoped connections. The application and test use the same SQL store, not a second booking implementation.

The fixed-source hosted Spring/MySQL check gated `Pricing.Client.quote` before it returned to `Booking.Service.reserve`; while this dependency call was held open, a separate JDBC connection successfully executed `SELECT id FROM events WHERE id=? FOR UPDATE NOWAIT` and rolled back its observation. Thus this exercised request had not acquired the event row lock while its pricing dependency was outstanding. After the gate released, the HTTP hold succeeded. The check also queried `@@transaction_isolation` **inside** `JdbcBookingStore.transact` and asserted `READ-COMMITTED`. Real test SQL and assertions are in `CheckoutRecoveryIT#dependencyFetchFinishesBeforeEventRowLock`; the source call order above is the production HTTP-path boundary. The test does not inject a slow real pricing HTTP service, so network timing distributions are not claimed.

The same check executed `EXPLAIN SELECT * FROM holds WHERE event_id='night'`; MySQL chose `ix_holds_event_status_expiry` with `type=ref`. Migration `V1__event_booking.sql` defines that index, `ix_orders_event`, the unique quote and hold/order keys, and the global `(owner,idempotency_key)` order key. Source and schema review show the order insert and hold status change occur in one transaction; a duplicate-key failure is translated outside that rolled-back transaction. `JdbcBookingIT#uniquenessConflictRollsBackAcrossSeparateRealConnections` checks the actual rollback via an independent connection.

`JdbcBookingStore` loads all holds and orders for one event under the event row lock. This is simple and sufficient for the small synthetic ten-seat correctness case, but work scales with accumulated event history. No throughput or production-scale inventory claim follows from the race test. Bounded SQL accounting, retention/archive policy, and larger-event load evidence remain future design work as documented in `docs/project/architecture.md` and G-0018. A failure or timeout under load is a distinct outcome; it must not be counted as `SOLD_OUT`.
